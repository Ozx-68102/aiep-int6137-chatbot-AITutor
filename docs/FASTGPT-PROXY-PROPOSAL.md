# FastGPT 接入与薄代理后端（提议）

本文记录 FastGPT 薄代理的**架构与分工提议**。`server/` 已经能流式转发对话。`src/api/chat.ts` 仍是本地示例回复。

## 背景

- 前端：React + Vite + TypeScript，聊天 UI 在仓库根目录的 `src/`。
- FastGPT：他人维护的云端实例（工作流、知识库、应用配置不在本仓库）。
- 目标：**流式**显示助手回复。

环境变量项见 [TECH.md](./TECH.md) 与根目录 `.env.example`；薄代理从根目录 `.env` 读取 FastGPT 相关配置。

## FastGPT 已是后端，为什么还要代理？

FastGPT 负责 AI 与工作流（检索、编排、调用模型等）。浏览器侧仍建议加一层**薄代理**（BFF，Backend For Frontend），在本项目里主要解决这些事：

| 动机         | 说明                                                                            |
|--------------|---------------------------------------------------------------------------------|
| 跨域         | 页面直连 FastGPT 域名常被浏览器拦截；服务端到服务端无此限制。                   |
| 流式转发     | 接收 FastGPT 的流式响应并转给浏览器（SSE 或等价流），统一超时与断线处理。       |
| 对内接口稳定 | 前端固定调用 `/api/...`；上游 URL 或字段变更时优先只改代理。                    |
| 分工         | 前端与代理在本仓库；FastGPT 控制台由维护者负责，代理按对方提供的 API 说明转发。 |

代理不是再造一个 FastGPT，通常只有少量路由（例如一个「发消息」接口）和转发逻辑。

## 是否与本仓库一起提交？

**可以。** 推荐增加独立目录（例如 `server/`），与根目录前端并列：

```
仓库根目录/
  src/              # 现有前端
  vite.config.ts
  server/           # 薄代理（登录、会话、发消息）
  .env              # 本地配置，不提交
  .env.example
  docs/
```

原则：

- 根目录仍以 **pnpm 构建与开发前端** 为主；`pnpm dev` / `pnpm build` 默认行为可保持不变，是否在文档中增加「同时启动代理」由团队决定。
- 不把 Python 虚拟环境、`node_modules` 提交进 git（`.env` 的忽略规则沿用现有约定）。
- 前端不 import 代理目录中的代码，只通过 HTTP 访问代理。

若课程对目录有硬性规定，可微调路径名；核心是**目录分离、HTTP 边界清晰**。

## 语言选择（Python 与 Node）

| 方案                     | 说明                                                                                                                   |
|--------------------------|------------------------------------------------------------------------------------------------------------------------|
| **Python**（如 FastAPI） | 适合熟悉 Python 的成员；异步 HTTP 客户端做流式转发即可。依赖放在 `server/`（`requirements.txt` 或 `pyproject.toml`）。 |
| **Node**                 | 与前端同生态，便于一人前后端兼顾；非必须。                                                                             |

代理层保持尽量薄，复杂业务仍放在 FastGPT 工作流。

## 职责划分

| 角色           | 负责内容                                                                                                                                                                      |
|----------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| FastGPT 维护者 | 应用、工作流、知识库；提供对话 API 说明（URL、鉴权、流式、请求体字段、`variables` 等）。                                                                                      |
| 薄代理         | 读取 `.env` 中的 FastGPT 配置；登录，以及账号上的语言等设置；会话列表，和会话 id 与 FastGPT `chatId` 的对应，写入服务器，重启后仍在；按维护者文档调用并流式转发；错误与超时。 |
| 前端           | 聊天 UI、多会话、`locale`；`src/api/chat.ts` 请求本项目代理；流式逐段更新助手消息。                                                                                           |

FastGPT 侧具体字段与示例以维护者文档为准；可在代理实现旁单独写对接备注，本文不罗列以免与真实环境不一致。

## 流式与前端行为（提议）

1. 用户发送消息后，展示用户气泡与加载状态。
2. 前端请求代理（`fetch` 读 `response.body` 流，或消费 SSE）。
3. 代理向 FastGPT 发起流式对话，将数据块转发给浏览器。
4. 前端将增量文本追加到当前助手气泡；结束或失败时结束加载状态。

多轮对话：前端 `session.id`（UUID）可与 FastGPT `chatId` 一一对应。一个会话里的消息由 FastGPT 按 `chatId` 保存。会话列表和这条对应关系由代理写在服务器上，重启后仍然在。不要只放在内存或浏览器里。

## 本地开发（提议）

两个进程：

1. 代理：例如 `http://localhost:3001`。
2. 前端：`pnpm dev`，在 `vite.config.ts` 将 `/api` 代理到上述服务，页面统一请求 `/api/...`。

这是小组作业。成品部署在专业老师设置的服务器上，使用本专业所属部门的公网域名，给其他人从公网访问。语言等设置和左侧会话列表存在服务器上，挂在登录账号下。可以先只有一个 `admin` / `admin`。同一个账号换一台电脑登录，看到的是同一份。

生产环境可由网关把静态资源与 `/api` 分别转发到前端构建产物与代理。

## 前端 ↔ 代理 接口（待团队敲定）

以下为**本项目内部**约定，与 FastGPT 字段无关。路径和响应格式实施前还需评审：

- `POST /api/chat`（路径可改，但应固定一种）。
- 请求体：`message`、`chatId`（必填）、`locale`（若工作流需要）。`chatId` 是当前会话的 id，缺了就拒绝。同一会话的后续消息继续带同一个 id。
- 响应：流式；实现时前后端统一为一种格式（SSE 或 chunked 流）。

## 评审时可看的架构项

1. 是否有独立代理目录，前端仅 HTTP 访问代理。
2. 流式是否在 UI 上逐块更新，而非长时间无反馈后一次性显示。
3. 代理对 FastGPT 的调用是否与维护者提供的文档一致。
4. 若采用 Python 代理，是否写明依赖安装与启动方式（可与 README 互链）。
