## <span id="sec0">引入：什么是包管理器</span>

【[返回标题](#title)】【[下一节](#sec1)】

Node.js 本身只提供了一个运行 JavaScript 的基础环境。而一个真实的项目要跑起来，几乎不可能所有代码都自己写——程序员不反复造轮子。因此，你会用到别人写好的库、框架，以及构建工具。这些来自第三方的代码需要一个地方下载、记录和整理。这就是**包管理器**的职责。npm 会随着 Node.js 一起安装，作为默认的包管理器；pnpm 则是后来出现的改进版本。

要理解它们，我们需要先知道两样东西：`package.json` 和 `node_modules` 。包管理器的所有行为最终都会围绕这两者展开。



## <span id="sec1">`package.json`：项目的「清单」和「身份证」</span>

【[返回标题](#title)】【[下一节](#sec2)】【[上一节](#sec0)】

`package.json` 是放在整个项目根目录下的一个 JSON 格式的文件。它定义了这个项目的作用和依赖。换句话说，它是项目的清单。而清单上最重要的东西就是**依赖声明**。这个声明分为两类——`dependencies` 和 `devDependencies`。

`dependencies` 指的是**项目在运行期间必须存在的组件**。比如你用 React 写页面，React 相关的依赖在程序跑起来的时候就必须存在。你用 Tailwind 美化页面，那 Tailwind 相关的依赖在运行时也必须存在。这些组件到哪都需要，不管是在开发还是在部署后运行，所以要放在 `dependencies` 里面。而 `devDependencies` 则是**只在开发阶段需要的工具**。举个例子，测试框架、代码检查工具（Linter），以及 Vite 都属于此类。它们只是帮助你更好地开发和打包，但最终程序运行起来的时候并不需要依赖它们运行。在仅仅只是将程序部署上线时，这些工具可以跳过不装。

以 React + Vite 的项目举例，`package.json` 的依赖部分大致长这样：

```json
"devDependencies": {
  "@vitejs/plugin-react": "^6.1.2",
  "vite": "^8.3.5"
},
"dependencies": {
  "react": "^19.3.1",
  "react-dom": "^19.3.1"
}
```

这里就要讲一下版本号前面的标识符是什么意思了。尽管这里只呈现了一个（`^`），但实际上还有一个（`~`）。以上面的 `^6.1.2` 为例，这个 `^` 的意思是「允许安装**版本号在 6.x.x 范围内的最新版本**」，最前面的那个数字不变；而如果把 `^` 换成 `~`，那就更严格，表示「**只**允许安装**版本号在 6.1.x 范围内的最新版本**」。有关于版本号的相关知识，可以去看看 [SemVer 语义化版本](https://semver.org/lang/zh-CN/) 。

其实 `package.json` 还藏着一个非常便捷的入口： `scripts`。你可以在里面定义一些命令别名，比如说：

```json
"scripts": {
  "dev:frontend": "vite",
  "dev:backend": "cd server/ && uv run uvicorn server.app:app --host 127.0.0.1 --port 3001",
  "build": "tsc --noEmit && vite build",
  "lint": "oxlint",
  "preview": "vite preview"
}
```

在定义之后，你在命令行里输入 `npm run dev:backend` 就等同于执行 `cd server/ && uv run uvicorn server.app:app --host 127.0.0.1 --port 3001` 这么一长串的命令。这是一种非常高效便捷的方法，任何新加入项目的人，他们都不需要知道具体是怎么启动的，只需要看一眼 `scripts` 就能启动程序，正常推进构建和测试流程。



## <span id="sec2">`node_modules`：清单中的「文件实体」</span>

【[返回标题](#title)】【[下一节](#sec3)】【[上一节](#sec1)】

前面介绍了 `package.json` 这个「清单」，现在我们就来讲讲它**落到实处**的地方——`node_modules`。这是个文件夹，用来安放实际下载好的第三方依赖。当你在命令行输入 `npm install` 这个命令的时候，npm 会读取 `package.json` 里面声明的**所有依赖**（包括 `dependencies` 和 `devDependencies`），解析出每一个依赖所需要的具体版本，然后把它们都下载到 **项目根目录下的 `node_modules` 文件夹里面**，如果没有这个文件夹，npm 会自己创建，然后再下载。项目里的代码在执行 `import` 或 `require` 的时候， Node.js 会到这个文件夹里面查找对应的依赖。

值得注意的是，这个文件夹通常是**不会提交到 Git**的，它会被写进`.gitignore`。因为它可以根据 `package.json` 和锁文件（`package-lock.json`，下文提及）重新生成。删掉这个文件夹，重新执行命令安装，它就会回来。另外，它非常大，通常会有几百 MB 甚至几个 GB，所以也不推荐提交到 Git。



## <span id="sec3">npm 是什么？</span>

【[返回标题](#title)】【[下一节](#sec4)】【[上一节](#sec2)】

如前所述，npm 是 Node.js 自带的包管理器，全称是 **Node Package Manager**。它随 Node.js 一起安装，不需要再额外下载。它的基本工作流程前面其实已经提到了，这里再详细提一次：**读取 `package.json` 里的依赖声明，把对应的文件和代码下载到 `node_modules` 里，并且把这次安装的结果记录下来**。

我们日常用到的命令其实就这么几个：

```bash
npm install # 读取 `package.json` 并安装全部依赖
npm install <package-name>	# 安装一个新的依赖包并写进 `dependencies`

# 2 种方法等价，安装新依赖包并写进 `devDependencies`
npm install <package-name> -D
npm install <package-name> --save-dev

npm run <scripts-name>	# 执行 `package.json` 里面的一个脚本
```

还有一个要讲的东西就是锁文件： `package-lock.json`。它由 npm 自动生成，记录每个依赖在项目中的**精确版本**和**下载地址**。`package.json` 里的标识符只是一个范围，每个人每台机器在不同时间，甚至不同国家或地区安装都有可能存在不同的结果。而锁文件会把项目中的范围固定下来，以确保团队成员装到的环境上一致的。所以**不建议**手动修改该文件，而且应该和 `package.json` 一样提交到 Git 上。



## <span id="sec4">npm 的问题？</span>

【[返回标题](#title)】【[下一节](#sec5)】【[上一节](#sec3)】

npm 在组织 `node_modules` 时采用的是**扁平化**的结构，它尽可能地把深层依赖提升到顶层，以减少各依赖内的嵌套。这解决了旧版 npm 的嵌套地狱，但又引入了两个更严重的问题。

1. **幽灵依赖**。因为依赖被提升到顶层，你的代码可以 `import` 一个**从未在 `package.json` 里声明过**的包——仅仅因为它是某个依赖的依赖，碰巧被提升上来。平时看着方便，一旦上游包调整依赖关系，这个未声明的引用就会突然失效。
2. **磁盘重复。** 扁平化只解决单个项目内部的嵌套深度，跨项目仍然各存一份。多个项目依赖同一个包，npm 就在每个项目的 `node_modules` 里各存一份，项目越多、依赖越深，重复越明显。

实际上，这两个问题的根源属于同一个问题：**npm 用「复制 + 提升」组织 `node_modules`**。复制带来磁盘冗余，提升带来依赖可见性失控。



## <span id="sec5">pnpm：换一种组织方式</span>

【[返回标题](#title)】【[上一节](#sec4)】

pnpm 的出发点是**不再复制文件**，也不会把所有东西都扁平化。

它把所有依赖文件统一存放在一个**全局仓库**里，项目里的 `node_modules` 通过**硬链接**指向这个仓库，同一版本的依赖在磁盘上只存一份。同时，`node_modules` 根目录下**只放你在 `package.json` 里直接声明过的依赖**，间接依赖被隔离在内部目录中。这样代码只能访问自己声明过的包，幽灵依赖从结构上不再可能发生。

安装 pnpm：

```bash
npm install -g pnpm
```

pnpm 的用法和 npm 高度一致：

```bash
pnpm install	# 安装 `package.json` 依赖
pnpm add <package-name>	# 加入新依赖
pnpm add -D <package-name>	# 加入开发环境依赖
pnpm run	# 等同于 npm run
```
