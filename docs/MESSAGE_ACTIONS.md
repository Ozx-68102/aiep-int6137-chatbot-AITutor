# 消息操作区：气泡下方的提示、重试与编辑重发

> 状态：设计定稿，未实现 ｜ 定稿 2026-11-04
> 本文取代 [EDIT_MESSAGE.md](EDIT_MESSAGE.md)：编辑重发的设计已并入，其待定问题全部有了结论（见「与旧文档的关系」）。

## 要解决的问题

三件事，都落在同一个位置——气泡下方的「脚注」：

1. **被停止的轮次没有持久提示，也没有重试入口（bug）**。现在按了停止，唯一的即时提示是输入区上方的琥珀色横幅（「对话已停止」），它可以被关掉；关掉之后页面上就没有任何标记了。回答下面那行内联灰字要刷新以后才出现，而且只覆盖写了一半文字的轮次——一个字都没写出来就被停的轮次，刷新后也没有任何提示，只剩一条孤零零的提问。被停的轮次也没有「重试」按钮：重试现在只给失败的轮次。
2. **一轮的提问改不了**。现在能改一轮的办法只有「重试」：原样再问一遍。问错了、字打偏了、想换个问法，都只能把同一句再问一次。
3. **将来的操作按钮没有归属**。复制、点赞点踩这些操作要来了，需要统一的挂载点和交互规则。

## 设计总览：每个气泡下面一条脚注

每个气泡（用户提问、助手回答）下方挂同一个脚注组件（实现命名建议 `MessageActions`），**常驻预留一小段高度**：一条矮的常驻条，操作按钮 hover 时淡入，按钮出现时页面不跳动（DeepSeek、Gemini 等产品的做法）。

- **hover 触发区**：气泡本身与脚注区域——鼠标在任一上面，脚注里的 hover 型按钮就出现。
- **两类内容**：
  - **常驻**：坏掉的轮次（失败、被停止）的状态提示和重试按钮。始终可见、不可关闭——坏掉的轮次必须始终留着恢复的入口。
  - **hover 出现**：编辑、复制、点赞点踩这些日常操作按钮。
- 流式输出中（三个点的等待气泡）不显示脚注。
- **触屏设备**：目前只支持桌面网页，不做触屏适配。将来若支持触屏，hover 型按钮改为常显。

## 内容矩阵

| 脚注位置 | 常驻内容 | hover 出现 |
|---|---|---|
| 助手气泡 · 正常轮 | — | 复制、点赞/点踩（第四期） |
| 助手气泡 · 失败轮 | 「消息生成失败」+ 重试按钮 | — |
| 助手气泡 · 被停轮（有半截文字） | 「对话已停止」+ 重试按钮 | — |
| 用户提问 · 最后一轮 | — | 编辑 icon（第三期）；复制（第四期） |
| 用户提问 · 更早轮次 | — | 复制（第四期） |
| 失败/被停且零文字（无助手气泡） | 状态提示 + 重试按钮，挂在用户提问下方 | 按最后一轮的规则 |

「零文字轮次」：上游一个字都没写出来就失败/被停。现在这种轮次的回答气泡会被整个去掉，状态提示无处可挂；定稿为挂在用户提问的脚注里。

### 状态提示的样式（已定）

- **文字**：偏灰（比正文黑浅一档，沿用现在「对话已停止」内联文字的 stone-500 灰系）。
- **「消息生成失败」icon**：lucide `CircleAlert`，**黄色**（amber 系）。
- **「对话已停止」icon**：lucide `CircleStop`，黑色——与输入区的停止按钮同一个 icon，「你按了停止」的因果一眼对上。
- **重试按钮**：黑色中性描边（替换现在 `FailedReply.tsx` 的红色 `btn-error` 样式），icon 沿用 `RotateCcw`。
- 状态提示**不再是独立的错误消息**。现在的实现是往消息流里插一条 `role:'error'` 的红框气泡（实时流程 `addErrorMessage`、刷新流程 `session/thread.ts` 的 `withFailureNotice` 合成）；改成由消息自身的 `failed` / `aborted` 标志直接渲染脚注，消息流里只留真正的对话内容。这也是状态收敛，方向与 [CHAT_STREAM_KNOWN_ISSUES.md](CHAT_STREAM_KNOWN_ISSUES.md) 第 1、4 条一致。
- 与轮次无关的错误提示（「无法连接到服务器」这类）统一归横幅，消息流里的无按钮红气泡退役。

### 编辑按钮与编辑框（第三期，交互已定）

- **只出现在最后一轮的用户提问下方**；更早轮次的提问不可编辑。这消灭了「改前面某一轮，后面的轮次怎么办」的问题——永远没有后面的轮次。
- icon 代替文字（lucide `Pencil`）。hover 在 icon 上：背景变深做提示，并**立刻**（无延迟）在下方显示 popover：「编辑」，就 2 个字。
- 点击展开编辑框：气泡原地换成自动长高的多行 textarea（复用 N2 多行输入的 autoGrow 方案，见 [improvement-research/frontend-chat.md](improvement-research/frontend-chat.md)）。**N2 是这一期的前置。**
- 编辑框按键：**Enter 或点「发送」= 发送；Shift+Enter = 换行；Esc = 取消。**Enter 被发送占用，键盘换行走 Shift+Enter；多行内容也可以粘贴进来。
- 发送等于把这一轮删掉、用新文字重新问一遍（用户视角等同「重试」）。**不做版本历史、不做分支**，沿用原结论，理由见附录。
- **发送失败的回滚（Gemini 式）**：发送没有成功（409「这场对话还有一条正在回答」、断网等）时，编辑过的文字塞回**输入框**，提问气泡恢复成编辑前的原文，被去掉的（半截）回答连同状态提示一并恢复。实现上：引擎在动界面之前把整轮快照下来，失败就整轮回滚。
- 新一轮回答流式输出期间，编辑按钮隐藏（此时输入区本来也已锁定）。

## 行为规范：重试与编辑重发是同一条路

都走现有的 `POST /api/chat` + `retryOf`（要重发的那一轮的编号）：服务器先删旧轮（我们 `message` 表的两行 + 上游 FastGPT 的记录），再用新的轮次编号开一轮。这条路对失败轮和被停轮同样有效（服务器不检查旧轮的状态）——所以**给被停轮次补重试入口，服务器侧零改动**，缺的只是 UI。

- 引擎签名泛化（采纳调研 N5 的建议）：`retryTurn(sessionId, turnId, editedText?)`。缺省 `editedText` 是重试（原文重发）；传了是编辑重发（本地先替换提问文字，再走既有流程）。
- **服务器配套修复（已定方案①）**：`_clear_failed_turn`（`server/src/server/app.py`）指认上游「悬空提问」（被停轮上游只记了提问）时，拿**请求体里的文字**与上游最后一条记录比对。重试时请求带的是原文，比得中；编辑重发时请求带的是新文字，永远比不中，悬空提问就删不掉。修法：**删轮之前从我们自己的 `message` 表里读出这一轮的提问原文**，用它来比对。接口不用加任何字段；顺带让重试也更稳（不再依赖页面把旧文字一字不差发回来）。「指认不了就不删，宁可上游历史多一遍问答」的保底原则不变。
- 已知边界（沿用现状）：被停轮之后用户又问过别的，悬空提问不再是上游最后一条，就不会被删——它会留在上游的上下文里。见 [INTERRUPTED_REPLY.md](INTERRUPTED_REPLY.md)「一个已知的副作用」。

## 警告横幅：职责与位置（已定）

- **职责**：横幅只留会话级事件——服务降级、「这场对话还有一条正在回答」（roundBusy）、停止没停住（replyStopFailed）、操作失败/连不上。**「对话已停止」彻底退出横幅**（改为脚注里的持久提示）。
- **位置**：横幅移出带 `border-t` 的输入区容器，作为聊天滚动区与输入区之间的流内兄弟节点。效果：**分隔线固定在输入区顶上不动**，横幅坐在线的正上方，出现时压缩消息区高度（消息上滚），不遮挡内容。「真悬浮盖在消息流上」的方案被否——不做复杂。
- 多条横幅纵向堆叠。
- 实施时顺带：`App.tsx` / `WarningBox.tsx` 里「聊天区顶部的警示框」的过期注释改掉；[UI_WARNINGS.md](UI_WARNINGS.md) 修订（横幅用例去掉「这一轮被停止」、失败提示的「红色描边气泡」描述改成本文的脚注样式、横幅位置语义写成「输入区分隔线上方」）。

## 未来的按钮（占位登记，不在本期）

## 附：为什么不做版本历史和分支

沿用 EDIT_MESSAGE.md 2026-11-01 的结论：

想过做成「可以留多个版本」：编辑过的消息底下显示 `<2/2>`，左右箭头翻看，选一个版本继续回答，最多改 5 次。**不做。**FastGPT 的上下文是**一条直线**（它按 chatId 查自己的记录）。选一个旧版本继续，就要把上游从分叉点往后**重写一遍**：删掉那些记录再重新问一遍。编辑第 3 轮，第 4 到 10 轮全部重答，token 和时间都白花一遍——纯折腾上游。我们的表倒是可以存成树（每版带父版本），但树只在我们这边，上游看不见；树的用处就靠「能在两套历史之间来回切」，切一次上游就得重写一次。存储本身倒不是问题：多出来的体积是按**编辑次数**长的（一次编辑多存一份那条文字，几百字节），不是按消息条数长的。

所以「编辑」就做最朴素的这一种：改完直接重发那一轮，跟「重试」一样，历史里始终一问一答。没有版本列表，没有分支，上游那边只动一轮。哪天上游换成我们自己管的组件（会话存储和上下文都是我们的），这个结论要重新算：那时候切一条分支只是「下次发哪几条消息」的事，不用重写上游、不用重答，版本历史和分支就都有价值了。到那时候再把这件事捡起来。

## 附：决策记录

2026-11-04 与维护者逐项讨论定稿：

- 警告横幅位置取「流内、分隔线上方」（b 案）；「真悬浮盖在消息流上」被否。
- 脚注常驻预留高度（一小段）；hover 型按钮淡入；触发区 = 气泡 + 脚注区域。
- 坏掉轮次的状态提示与重试按钮常驻、不可关闭；状态文字偏灰；「消息生成失败」icon 为 `CircleAlert` 黄色；「对话已停止」icon 为 `CircleStop` 黑色；重试按钮黑色描边。（icon 从 16 个候选里选出，候选对照表生成于本地工作区 `scratch-visual/`，不入库。）
- 非轮次的错误提示归横幅，消息流里的无按钮红气泡退役。
- 编辑只给最后一轮的用户提问；Enter 发送 / Shift+Enter 换行 / Esc 取消；发送失败按 Gemini 式回滚（文字进输入框、气泡复原、回答复原）。
- 服务器悬空提问匹配修复取方案①（从我们自己的 `message` 表读旧提问原文比对）。
