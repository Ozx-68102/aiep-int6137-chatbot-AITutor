# Findings

记实际看过、但文档或接口说明里不明显的行为。新的发现按日期追加在下面，不要把密钥、密码或 cookie 写进来。

## 2026-10-26 FastGPT 删除不存在的会话仍返回 200

访问地址本身以 `/api` 结尾。删除一场会话的上游地址是：

`DELETE {访问地址}/core/chat/history/delHistory?chatId={会话id}&appId={应用id}`

用一个从未说过话、上游没有记录的会话 id 调用，HTTP 状态仍是 200，正文是：

```json
{"code": 200, "statusText": "", "message": "", "data": null}
```

所以「这场会话在 FastGPT 里不存在」和「删除成功」看起来一样。我们的 `DELETE /api/sessions/{会话id}` 收到这个结果后，仍然删除自己数据库里的会话，并清掉 Redis 里的半截文字。上游返回 404 时同样删除本地。只有上游返回其他错误时，本地会话才保留。

## 2026-10-26 官方接口里没有「分享某一场会话」

[API 文档介绍](https://doc.fastgpt.io/zh-CN/openapi/intro) 写明：从 4.15.0 起，手工维护的接口说明不再更新，最新列表在部署地址的 `/apidoc/devapi` 和 `/apidoc/systemopenapi`。

（2026-10-31 补：我们这个部署是 v4.14.5 基线，这两个地址都是 404 —— 它们 4.15.0 才有，v4.14.5 的源码里没有任何 apidoc 相关页面。整份接口清单要对着 v4.14.5 的源码看，详见下面 2026-10-31 那条。）

[对话接口](https://doc.fastgpt.io/zh-CN/openapi/chat) 里，和某一场 `chatId` 有关的操作是：列会话、改标题、改置顶、删除这场会话、取基本信息、取消息、取运行详情、删一条消息、点赞或点踩。没有「把这一场对话分享出去」的接口。

（2026-10-31 补：这份清单来自文档站，对应的是更新版本；v4.14.5 自己的文档源码里同样没有「停止」。）

文档里的「分享」指的是应用的免登录窗口：在控制台的发布渠道里创建一条链接，地址带 `shareId`，打开的是整个应用，不是我们某一场会话。清空会话的说明也把「分享链接」和 API 创建的会话分成两种来源。

因此不把 FastGPT 的免登录窗口当成我们的分享。以后如果要分享某一场会话，做法是读出这场已经完成的消息，把用户提问和助手回复写成 Markdown 再下载。现在没有这个需求，先不做。置顶只存在我们自己的数据库里，不调用 FastGPT 的置顶接口，因为生成回答用不到它。

## 2026-10-26 助手回复开头的空行来自上游正文

页面用 `whitespace-pre-wrap` 显示助手文字，不会自己插入换行。后端把 FastGPT 的 `delta.content` 原样放进 SSE，历史记录也是把上游 `text.content` 拼起来。实测「你好」的回答正文以两个换行开头，所以气泡顶部空出两行。页面显示时去掉助手文字开头的换行，中间的换行仍保留。

置顶时刻由页面在置顶时传给服务器，字段是 `pinned_at`。取消置顶时清空。页面按这个时间把较早置顶的排在上面，不再记在这台浏览器里。

## 2026-10-29 会话标题原来只存在浏览器内存里

新建会话时，页面把首条提问写进自己的状态当标题，但没发给服务器，`session` 表的 `title` 一直是 NULL。
刷新页面时列表从 `GET /api/sessions` 读回 NULL，标题就退回占位文字（新对话）。

`PATCH /api/sessions/{会话id}` 是唯一能写标题的接口，之前只被手动重命名用到；它也从来不写 `title_locale`，
所以 `session.title_locale` 这一列在库里一直是 NULL，标题上的 `lang` 属性等于没有。

现在改成：建会话时 `POST /api/sessions` 可以带上 `title`，一次写进数据库；
标题为 NULL 的旧会话在发出下一条消息时用 `PATCH` 补写一次。标题最长 500 字，超出后端返回 422，页面自己先截断。

标题的内容就是首条提问原文：FastGPT 没有生成标题的接口，本仓库里也没有，这是目前能做到的最好做法。
老会话的标题不回填，是有意留着：它们下次发消息时用那次的提问当标题。
标题没存进数据库时，页面退回占位文字，不出现「看着有标题、库里没有」的情况。

`session` 表里还有一列 `title_locale`，本来是给标题加语言标记用的，读屏软件按这个标记选语音念标题。
这个功能先不做：只有简体中文、繁体中文、英文三个取值，标题里混了别的语言就标不对，
不如不标。所以接口不再返回这一列，也不再写它；表里的列没动，将来做的时候直接用。

## 2026-10-29 重复点「创建新对话」不新建，也不提示

点「创建新对话」不会马上在服务器上建会话。页面只是进入"正在写新会话"的状态：把草稿存起来，
清掉当前选中的会话，切到聊天页。真正建会话是发出第一条消息的时候才做的，`POST /api/sessions` 那时才调。

已经在"正在写新会话"的时候再点一次，页面什么都不做：不新建，不报错，也不提示。
`src/App.tsx` 的 `addSession` 里看到 `composingNew` 为真，就 `setView('chat')` 直接返回。

这是有意为之，不是漏了提示。服务器那边也拦不住连续建空会话，它只负责建，不管建出来的会话有没有内容。

## 2026-10-29 FastGPT 一整块返回，不是逐字

我们给 FastGPT 传的是 `stream: true`，响应头也是 `text/event-stream`，但实测上游不是逐字吐字。
连续三次对话都是这个节奏：先来一个只含换行符的事件，隔 2 到 5 秒整段答案一次性到达，
再来一个换行符事件，最后是 `finish_reason` 和 `[DONE]`。

第一个事件在 0.3 秒左右就到了，第二个事件隔了好几秒，所以不是反向代理把响应攒住才发，
是 FastGPT 那边（maas.eduhk.hk）自己把答案写完才写成一条事件。要改成逐字输出是那边的事。

因此「半截回答」现在基本不会从上游出现，Redis 里那份文字主要用来接住「页面断开、服务器还在写」
这种情况。页面靠 `/api/sessions/{会话id}/partial` 的 status 判断：`streaming` 是还在写，
`finished` 是写完了，`failed` 是中途断了（上游报错或者连接断了）。上游失败时后端把状态写成
`failed` 并保留已写出的文字，页面据此显示半截回答和一个红色提示。

## 2026-10-30 刷新页面时，用户提问和「…」会一起消失（已修）

原因不在 Redis，在前端的归位逻辑。

`src/session/thread.ts` 的 `withPartial` 靠「线程里最后一条助手消息的文字是不是以 Redis 里那份
文字开头」来判断当前这一轮对应哪条消息。刷新发生在第一块字到达之前，Redis 里的文字是空串，
`startsWith('')` 恒成立，于是把**上一轮**的回答标成了「正在写」：

- 上一轮回答有文字，「…」就不会出现（`waitingForText` 要求文字为空）；
- 接着 `resumePartial` 找到的也是上一轮那条，轮询时新文字拼不进去（`partial.text` 不是上一轮
  文字的开头），这一轮的回答在刷新后的页面上永远不出现；
- 用户的提问本来就没地方存：后端只把它转发给 FastGPT，Redis 只存助手那半截文字，
  我们自己的库里没有消息表。FastGPT 又是这一轮结束之后才把记录写进它的库。

所以刷新那一刻，「你问了什么」在服务器上哪儿都没有，页面自然就空了。等到模型答完再刷新，
FastGPT 的历史里才有这一轮，页面才恢复。

日志能对上：20:15:33 发出提问，20:15:34、20:15:35、20:15:36 连续三次刷新，每次都是先读
`/partial` 再读 `/messages`，而那一刻 `/messages` 拿不到这一轮；20:15:40 上游整段到达，
20:15:41 `[DONE]`；20:15:42 再刷新，页面才完整。

现在改成：每一轮有自己的编号，Redis 里连着提问一起存着，服务器把「正在写的那一轮」接在历史
后面一起返回，页面按编号认消息，不再靠文字猜。详见 [INTERRUPTED_REPLY.md](INTERRUPTED_REPLY.md)。

## 2026-10-30 刷新得太急，上游会被打垮，日志会被撑爆

21:18 的一次实测：发出提问以后连着刷新了十来次，每次刷新都问一次 FastGPT 要整段历史。
上游（maas.eduhk.hk）从 21:18:18 起连不上了 —— 报的是 `httpx2.ConnectTimeout`，
也就是 TCP 连接根本没握上，不是响应慢。紧接着 21:18:24 连聊天本身也失败了
（「FastGPT 读取失败」）。

三个后果，都改掉了：

1. **上游被打垮**：每一次页面加载都要问一次上游要历史，刷新得急了就是几十个并发请求。
   现在服务器留五秒的缓存，刷新多少次上游就只被问一次（实测：连着刷新十次，上游被问两次）。
2. **日志被撑爆**：一次失败打 250 行。`app.py` 的通用异常处理器打一遍栈，Starlette 处理完
   还会把异常再抛一次，uvicorn 又打一遍栈。现在网络错误（连接超时、读超时）在 FastGPT 客户端
   就被收成 `FastGPTError`，接口回一个 502 和一行字，不打栈；通用处理器也只记一行。
3. **错误信息对用户没有意义**：上游挂掉时页面只说「暂时问不到上游，请稍后重试」。

## 2026-10-30 FastGPT 的几个接口事实

对着[官方对话接口文档](https://doc.fastgpt.io/zh-CN/openapi/chat)和 FastGPT 源码核过：

- `DELETE {访问地址}/core/chat/history/delHistory` 的注释是 "delete single chat history (soft delete)"，
  它把**整场会话**标记成删除，也就是清空整场上下文，没有「删一轮」这个选项。
- 源码里另有删单条记录的接口，官方文档没有列它。（2026-10-31 更正：v4.14.5 里是
  `POST {访问地址}/core/chat/item/delete`，body 是 `{appId, chatId, contentId}`，实现是给那条记录写
  `deleteTime`（软删），按 `dataId` 匹配。早先这里写的 `core/chat/record/delete` 和
  `sourceType`/`sourceId`/`contentIds` 那套参数属于更新版本，v4.14.5 没有那个文件。）
- `responseChatItemId` 会把客户端给的值当作本次回答的 ID 存进 FastGPT 的数据库（同一 chatId 下要唯一）。
  实测（21:22）：传 `responseChatItemId=turn-test-0001`，再用 `getPaginationRecords` 读回来，
  那条 AI 记录的 `dataId` 就是 `turn-test-0001`，Human 记录的 `dataId` 是 FastGPT 自己的。
  我们的编号因此能跟着回答回到历史里。
- chatId 传非空时，FastGPT 只把 messages 数组最后一条当用户问题，其余全部忽略；
  chatId 不传时，它不用自己的上下文，完全靠我们传入的 messages 构造上下文。

## 2026-10-30 Safari 的网站图标

SVG favicon 在 Safari 26 之前一直不支持（[caniuse](https://caniuse.com/link-icon-svg)：
Safari 3.1–18.7 不支持，26 起支持；Chrome 80 起就支持）。所以老 Safari 上 tab 里显示不出图标，
要准备一份 PNG。

另外 Safari 的 favicon 缓存是按**页面地址**记的：某个地址缓存成「没有图标」之后，
重新加载同一个地址它也不会再取一次，换成带查询参数的地址（新的缓存键）才会重新取。
这就是「根目录没有图标，带上 ?session=xxx 刷新才有」这种现象的来源。

## 2026-10-31 FastGPT 的版本基线是 v4.14.5，接口清单看源码不看文档站

我们这个 FastGPT 是内部部署的，基线是 **v4.14.5**（内部可能有改动，别当原版用）。它的接口说明分三层：

1. 代码里的 OpenAPI 定义（`packages/global/openapi/**`），每个路由带 summary 和 description，是给自动生成的接口清单用的；
2. 文档站的手写页（`document/content/docs/**`）；
3. 部署地址上的自动清单 `/apidoc/devapi` 和 `/apidoc/systemopenapi`。

第 3 层是 4.15.0 才引入的，v4.14.5 的源码里没有任何 apidoc 相关页面，所以在我们部署上这两个地址都是 404（返回的是前端页面）。第 2 层对应的是更新版本的文档：v4.14.5 自己的文档源码 `document/content/docs/introduction/development/openapi/chat.mdx`（「对话接口」页，1248 行）里没有「停止」两个字。

所以「文档里没有、源码里有」在 FastGPT 是常态，两边都不是接口全集。要确认某个接口存不存在、地址和参数是什么，看官方仓库 tag v4.14.5 的源码，再实测一次。取单个文件不用克隆整个仓库：

```bash
curl -sL https://raw.githubusercontent.com/labring/FastGPT/v4.14.5/<路径>
```

## 2026-10-31 FastGPT 的停止接口只对 v2 有效，我们走 v1

v4.14.5 有 `POST {访问地址}/v2/chat/stop`：body 是 `{appId, chatId}`，鉴权走 `authChatCrud`（API key 可以）。它做的事是往 Redis 写一个标记 `agent_runtime_stopping:{appId}:{chatId}`（TTL 60 秒），然后每 50 毫秒轮询这个标记，最多等 5 秒，标记没了就返回 `{success: true}`。源码：`projects/app/src/pages/api/v2/chat/stop.ts`、`packages/service/core/workflow/dispatch/workflowStatus.ts`。我们部署上这个接口存在，认我们的 API key（实测返回 `{"success":true}`）。

但它对我们没用。调度器 `packages/service/core/workflow/dispatch/index.ts` 里的判停函数分两种：

- `apiVersion === 'v2'`：看上面那个 Redis 标记（每 100 毫秒轮询一次）；
- `apiVersion === 'v1'`：只看客户端连接断没断（`res.closed || res.errored`）。

v1 的路由 `projects/app/src/pages/api/v1/chat/completions.ts` 传的就是 `apiVersion: 'v1'`，我们打的也是 `/v1/chat/completions` → 那个标记没人读。

实测（2026-10-31）：同一句问题，第 1 秒时调停止接口，连做 4 次，每一轮都跑完、都有完整回答、都有 `[DONE]`。停止接口的耗时（0.98 / 5.19 / 5.32 / 6.17 秒）只是跟着那一轮自己什么时候结束走（运行结束时会删掉标记），跟有没有被停掉无关。

另外每轮**开始**时调度器会先删掉停止标记（源码注释 "Remove stopping sign"），所以「先停止、后发这一轮」这种次序也一定不生效。

对 v1 有效的停止信号只有一个：我们自己断开到上游的连接 —— 也就是我们 cancel 掉 httpx 请求时发生的事。FastGPT 在下一个节点边界停下（判据就是客户端断开），已经在跑的那个节点会跑完。

（2026-10-31 更新：我们已经改走 v2，见下面「我们改用 v2/chat/completions」那条。）

## 2026-10-31 停止请求和对话请求谁先到，决定这一轮停不停得住

按停止时，页面发两条请求：一条是它自己那条流的中止（浏览器本地），一条是 `POST /api/sessions/{会话id}/abort`。服务器那边只有第二种能停住上游。

问题在于这两条请求和「对话请求」是三条独立的 HTTP 请求，服务器按到达顺序处理。原先中止接口只能取消「已经登记在跑的那一轮」（`_running` 里的任务），所以：

- 对话请求先到 → 中止接口找到任务，取消掉，这一轮停住；
- 中止请求先到 → 那一刻还没有任务可取消，中止接口空转返回 204，那一轮照跑完。

实测（2026-10-31）：对话请求走一条新连接、中止请求走一条已经连着的空闲连接时，中止的字节先到服务器，**十次里十次停不住**。停不住的后果是页面显示「已停止」，答案其实写进了 FastGPT 的历史、要刷新才看得到，期间再发一条还会吃到 409。

修法：中止接口先写一个停止标记（Redis，键 `h2botapp-chat:{会话id}:stop`，值是这一轮的编号，一分钟过期），对话接口在开这一轮之前先看这个标记 —— 编号对得上就不开这一轮，只把提问登记下来。标记按编号认，只对那一轮有效。

另外两处一起改了：

- 中止接口取消任务之后，等这一轮真的收尾（最多两秒）再返回，这样页面紧接着读 `/partial` 读到的是最终状态，不会读到还在写的中间状态。
- 页面不再自己宣布停了：按停止之后去读 `/partial`，服务器说停了就显示警示框「对话已停止」，说还在写就接着等，说写完了就把答案补上。

实测（2026-10-31）：中止先到 → 上游一次都没被问，流直接结束，`/partial` 是 `{"status":"aborted"}`；对话先到 → 那一轮被掐掉，`/partial` 同样是 `aborted`；老客户端不带编号 → 服务器自己认当前这一轮，照样掐掉；停过之后发新一轮 → 正常跑完（`[DONE]` 收到，状态 `finished`）。

## 2026-10-31 会话行上的 transform 会把行内的浮层关进去

会话行有重新排序的动画，动画期间行上会带 `transform: translateY(...)`（`Sidebar.tsx` 里直接写
`row.style.transform`）。这一下有两个副作用：

- 带 transform 的元素会**建立层叠上下文**，行内那个 `fixed z-50` 的二级菜单的层级就被关在这一行里，
  排在后面的会话行画在它上面 —— 菜单被后面的会话卡片盖住，点「重命名」「删除」点到的其实是下面那一行；
- 带 transform 的元素还是 `position: fixed` 的**包含块**，浮层的位置是相对这一行算的，不是相对视口。

所以二级菜单改成用 `createPortal` 挂到 `body` 上（`SessionRow.tsx`），位置直接按视口算：
`top` 用按钮的 `getBoundingClientRect().bottom`，`right` 用 `window.innerWidth - rect.right`。
点外面关菜单的判断也要改成同时看菜单本身和那个按钮（菜单已经不在按钮的父节点里了）。

教训：行内浮层（菜单、下拉）一律走 portal，不要挂在带 transform 的行里。

## 2026-10-31 接口服务连不上时，页面要自己撑住登录态

接口服务断掉时，浏览器里的 `login` cookie 还在，但页面读不到用户信息（`/api/profile` 读不到），
左下角的用户名就空了，看起来像掉登录了。另外「连不上服务器」被报了两遍：服务状态那边一条
琥珀色，动作失败那边又一条红色。

现在的做法：

- **用户名和语言记在本地**：`src/session/profile-cache.ts` 把它们放在 localStorage 的
  `h2bot-profile` 里，读到就写，退出登录清掉。页面启动时先用本地那份，接口服务连不上也照样
  显示用户名和原来的语言。
- **「连不上服务器」只报一次**：连不上的动作不再单独报一条红色，统一归到服务状态
  （`markService('unreachable')`），聊天区上方只有那一个琥珀色的框。
- **接口服务回来，页面自己恢复**：状态轮询（每 30 秒一次，`/api/status`）发现服务从「连不上」
  变回「正常」，就重新拉一次会话列表和用户信息（`refreshWorkspace`），不用用户手动刷新页面。

实测（2026-10-31，无头 Chrome 走 DevTools 协议）：在线 → 断掉服务并重新加载页面 → 聊天区上方
只有一个「无法连接到服务器，请稍后重试」，没有红色重复提示，用户名还在；服务起来之后提示自己
消失，三条会话自己回来了。

## 2026-10-31 异步接口里的同步数据库调用会卡住事件循环

FastAPI 里 `def`（同步）的接口跑在线程池里，不占事件循环；但 `async def` 的接口里直接写
`with db_session()`，整个事件循环就被卡住 —— 卡住的时候，正在流式输出的那一轮发不出去，
停止请求也进不来（这就是停止偶尔停不掉的另一半原因）。

本仓库受影响的只有四个异步接口：`/api/chat`、`/api/sessions/{id}/abort`、
`/api/sessions/{id}/messages`、`DELETE /api/sessions/{id}`。其余接口都是同步的，没这个问题。

改法：异步接口里碰数据库的那一步放到线程里（`await asyncio.to_thread(_authorize_session, ...)`，
`app.py` 里的 `_authorize_session` / `_delete_session_row`）。

实测（2026-10-31，本机 PostgreSQL）：数据库一次查询中位 **0.30 毫秒**，最大 78 毫秒（第一次
要开连接）；Redis 一次写入中位 **0.09 毫秒**。所以 Redis 那几处（每轮状态、半截文字）留在
事件循环里没问题，数据库那几处值得挪走。改完之后：停止请求从发出到返回 17 毫秒，
`/partial` 读到 `aborted`，流里没有 `[DONE]` —— 停止照旧灵。

## 2026-10-31 我们改用 v2/chat/completions

FastGPT 的 v1、v2 两个接口（`projects/app/src/pages/api/{v1,v2}/chat/completions.ts`）几乎
是同一个文件：逐行 diff 下来，实质差异只有两处 —— 传给调度器的 `apiVersion`，以及节点级
数据是运行中就写还是结束时一次写。请求体、消息解析、历史合并（最后一条当提问，其余和库里
的历史拼接）、`responseChatItemId`→`dataId`、SSE 帧格式，全都一样。两个接口也都要求 app
发布为 version v2（`app.version !== 'v2'` 就拒绝："您的工作流版本过低"）。

`apiVersion` 只决定工作流怎么知道自己该停（`packages/service/core/workflow/dispatch/index.ts`）：

- `v2`：看 Redis 标记 `agent_runtime_stopping:{appId}:{chatId}`（TTL 60 秒，每 100 毫秒轮询
  一次），标记由 `POST {访问地址}/v2/chat/stop` 写；
- `v1`：只看客户端连接断没断（`res.closed || res.errored`）。

**v1 那套在 v2 上不管用**：v2 的判停函数根本不看连接状态。所以切到 v2 的同时必须改成
主动叫上游停，否则停止会静默失效。

实测（2026-10-31，对着真部署，同一句「写一篇 800 字左右的短文」，第 2 秒按停止）：

|                            | FastGPT 那边存下来的这一轮                |
|----------------------------|-------------------------------------------|
| 带 `v2/chat/stop`          | 问 22 字，答 **1 字**（答案节点没跑起来） |
| 不带（对照，把那行注释掉） | 问 22 字，答 **684 字**（整篇跑完了）     |

也就是说：不主动叫停，光断连接，上游会把整篇写完 —— token 白花。

另外量到的几件事：

- `detail: false` 时 v1、v2 的帧一模一样（换行、整块答案、换行、收尾、`[DONE]`，共 5 帧），
  我们前端的解析一行都不用改。
- `detail: true` 时 v2 会多出一整套结构化事件：`flowNodeStatus`（节点名，比如
  「準備動畫和動手活動」）、`flowNodeResponse`（每个节点的输出和耗时）、`updateVariables`、
  `workflowDuration`、`fastAnswer`。**我们的部署已经开着运行状态**（实测这些事件现在就在发）。
  这是后面做「图片/视频生成要等几分钟」的进度显示能用上的东西 —— 后端挑着转给页面就行，
  不用 WebSocket。
- 停止接口自己会等工作流收尾，最多五秒（`waitForWorkflowComplete`）。所以我们的中止接口
  不能等它的返回：发出去就不管，页面等的是我们自己的状态。实测我们的中止接口 9～17 毫秒返回。
- 停止接口的返回体是 FastGPT 自己的壳：`{"code":200,...,"data":{"success":true}}`，
  成功要看 `data.success`。
- 切到 v2 之后，历史记录变胖：v2 把节点输出一起存进记录，而
  `core/chat/record/getPaginationRecords` 的字段是写死的（没有 `field` 参数可挑），
  返回里会带 `responseData`。我们只解析 `value[].text.content`，用不上但要传。
- 每轮**开始**时调度器会先删掉停止标记（"Remove stopping sign"），所以「停止信号早于上游
  开工」那几百毫秒的窗口里标记会被抹掉、这一轮照跑。v1 没这个问题（连接断开是持续状态）。
  那个窗口很小（上游从收到请求到开始跑工作流约 100 毫秒），而且我们的本地停止标记能兜住
  顺序问题，页面也已经有「没能停掉」那条路。

顺带看见的：工作流里已经有「有沒有上載題目圖／檔案？」和「Append validated visual after
teacher reply」这类节点 —— 上传和出图的工作流基础可能已经有了，缺的更可能在我们这边
（上传入口、把答案里的 markdown 变成真的图片）。

## 2026-10-31 删一条记录：源码里有，部署上也认我们的 API key

`POST {访问地址}/core/chat/item/delete`，body 是 `{appId, chatId, contentId}`。
鉴权走 `authChatCrud`（`authApiKey: true`），官方文档没有列它
（源码：`projects/app/src/pages/api/core/chat/item/delete.ts`）。

实测（对着真部署）：

- 它给那条记录写 `deleteTime`（软删），按 `dataId` 匹配。删完 `getPaginationRecords` 里就没有了。
- 删一个不存在的 `contentId` 也返回 200（正文 `{"code":200,...,"data":null}`），不报错。
- **回答那条的 `dataId` 就是我们的 `responseChatItemId`**；**提问那条的 `dataId` 是 FastGPT 自己的**
  （一串二十几个字符）。

所以重发一轮时两条都能删：回答按我们的编号删，提问从记录里找出来删。
工作流跑完了（记录里有回答）就按编号找，找不到回答就按「最后一条记录是不是同一句提问」找 ——
只有它就是最后一条记录时才删，否则那不是我们那一轮。

## 2026-10-31 重发一轮：上游的历史里不该出现两遍问答

重发用同一个 chatId 再问一遍，上游会再记一条提问和一条回答，历史里就有两遍问答。
做法是发之前把上一轮留在上游的记录删掉。

实测（对着真部署，2026-10-31）：问一句 → 上游一条提问一条回答；带 `retryOf` 再问一遍 →
上游最后只剩一条提问一条回答，我们的历史接口也是两条（一条提问、一条回答）。

顺带定下来的一件事：**同一个请求发两次只生成一遍**。服务器拿请求里的轮次编号对一下
Redis 里记着的当前轮次，对得上就是同一个请求又来了，不再开新一轮（正在写的那一轮回 409，
已经写完的那一轮回一个空的流，页面读 `/partial` 知道结果）。
以前没有这道门，重复点击或页面重发都可能让上游生成两遍。

还有一个坑：**刷新以后看到的提问是上游的记录，上游不知道我们的轮次编号**，
所以重发时不能靠编号找提问，要按位置找（失败提示前面最近的一条提问）。
