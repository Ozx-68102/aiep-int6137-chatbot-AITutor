# 会话标题：这一轮的改动和还没定的事

日期：2026-10-29
起因：新会话发第一条消息后，侧边栏标题变成首条提问，但刷新页面后又退回「新对话」。

## 已经改掉的

- 建会话时标题一起入库：`POST /api/sessions` 现在接受可选的 `title` 和 `title_locale`，
  页面发第一条消息时把首条提问（trim 后、最多 500 字）当标题一起发过去，
  标题和会话在同一个事务里落库。
- 旧会话（库里标题是 NULL）在发出下一条消息时，用 `PATCH /api/sessions/{会话id}` 补写一次标题。
- `PATCH /api/sessions/{会话id}` 现在也写 `title_locale`；请求里带了才改，不带就保持原值。
  手动重命名会带上当前界面语言。
- 页面显示的标题直接用接口返回的值，不再是页面自己另算的一份。

改动位置：`src/App.tsx`、`src/api/session.ts`、`src/session/title.ts`（新文件）、
`server/src/server/app.py`、`server/src/server/types/api.py`、`server/src/server/types/__init__.py`。

## 已经定下来的

1. **历史会话不回填。** 库里已有的会话标题保持 NULL，不写脚本补。
   这些会话等以后再发消息时，会用那次的提问当标题。
2. **标题就用首条提问原文。** FastGPT 那边没有生成标题的接口，本仓库里也没有，
   所以「拿首条提问当标题」是目前能做到的最好做法。最多 500 字，侧边栏靠 CSS 截断显示。
3. **标题保存失败时退回原来的文字。** 原来是显示占位文字（新对话）的会话，
   如果标题没存进数据库，页面也退回占位文字，界面和数据库始终一致。

## 还没定、留给你拍板的

4. **手动重命名时 `title_locale` 怎么处理。** 现在是这样：手动重命名时，标题的语言标记
   会跟着当前界面语言走。另一种做法是保留原来的标记。详见下面的说明。
5. **自动标题和手动重命名的先后。** 页面会等自动标题那次请求结束再做手动重命名，
   免得手动改的名字被自动标题盖掉。详见下面的说明。

## 上面两条的说明

**第 4 条（`title_locale`）**
`title_locale` 是标题的语言标记，取值 `zh-CN` / `zh-TW` / `en`。页面拿它给标题加 `lang` 属性，
屏幕阅读器按这个属性选语音读标题：标记是英文就用英文语音读。
现在的行为是：手动重命名时，标记跟着当前界面语言走。
问题是，你在设置里把界面切成英文，再给一个中文标题改名，这个中文标题的标记就变成英文了，
屏幕阅读器会用英文语音读它。
另一种做法是：手动重命名不动标记，标题原来是什么语言就还是什么语言；
原来没有标记的（历史会话都是没有的），就仍然没有。

**第 5 条（先后顺序）**
标题为空的旧会话，第一次发消息时页面会悄悄存一次标题（就是首条提问）。
如果这时用户正好又打开菜单手动改名，两次请求都改同一个字段，谁后到谁说了算，
可能出现「手动改的名字又被自动标题盖回去」。
现在的做法是：手动改名之前，先等自动那次存完，再发手动那次。

## 还没验证的

- 浏览器里的实际点击流程没验过（这一轮没有浏览器工具）。接口层用 curl 验过：
  带标题建会话、老方式建会话、重命名带/不带 `title_locale`、非法 `title_locale` 返回 422、
  超长标题返回 422，另外直接查 Postgres 确认了行确实写进去了。
- 页面在真实环境里发第一条消息时，标题是否和库里完全一致，需要你点一遍确认。

## 顺手记下的其它发现

- `POST /api/sessions` 以前不接受任何请求体，现在接受可选请求体，老的调用方式仍然能用。
- `PATCH /api/sessions/{会话id}` 以前只认 `title` 字段，多余字段会被静默忽略——
  所以历史上前端曾经发过 `title_locale`，后端却一直没存。
