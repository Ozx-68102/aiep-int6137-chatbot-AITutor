# 回答中断：现在的做法和接下来要做的

## 现在是什么样

一轮回答从后端到页面是这样走的：

- 页面 `POST /api/chat`，后端先登记「这一轮开始了」（写进 Redis），再起一个后台任务去问 FastGPT，同时**立刻把响应头发回去**。
- 流里只有两种东西，都是 FastGPT 的原样：`data: {"choices":[...]}` 是正文，`data: [DONE]` 是「写完了」。
- 后端把这一轮已经写出来的文字记在 Redis 里（`h2botapp-chat:{会话id}:text`），同时记一个状态：`streaming`（还在写）、`finished`（写完了）、`failed`（中途断了）。
- 页面断流之后读 `GET /api/sessions/{会话id}/partial`，就知道服务器那边到底怎么了。

上游中途失败时，实际发生的是：

1. 后端转发了几块内容，然后发现连接断了或者等太久了，把状态记成 `failed`，已写出的文字留着。
2. 流直接结束，没有 `[DONE]`。
3. 页面看到「流结束但没有 `[DONE]`」，判定「没写完」，去读 `/partial`。
4. 状态是 `failed`，于是显示「消息生成失败」的错误提示，位置在助手那条（半截）回答的下面。

这段是实测过的：让上游吐出一块内容就断线时，聊天接口吐出一块内容后没有 `[DONE]`，`/partial` 读出来是 `{"status":"failed","text":"..."}`。

## 已经做掉的

### 对页面的约定只有三条

| 页面看到 | 意思 |
|---|---|
| 200 + `[DONE]` | 写完了 |
| 200 + 流结束但没有 `[DONE]` | 没写完 |
| 非 200 + `{"detail": ...}` | 后端没接下 |

流里不增加任何新格式，只用 FastGPT 现有的两种帧。页面的解析代码可以照着 FastGPT 的接口文档写。

### 响应头先回，上游出问题时流直接结束

原来后端要等上游第一块内容才回响应头，浏览器里的那个请求要悬着 0.3 到 5 秒。这段时间里断网，页面会以为请求没落地而重发，服务器就生成两遍。

现在响应头立刻回（实测 0.013 秒），上游的失败一律变成「流提前结束」。

### 三个超时

原来 `read=None`（无限等），上游接了连接一直不吭声，这一轮会永远挂着，页面的三个点也永远转。现在：

| 位置 | 上限 | 依据 |
|---|---|---|
| 连接 | 10 秒 | httpx 的 connect 超时 |
| 读（等第一个字节、两块字之间都是它） | 30 秒 | 实测 0.3 到 5.2 秒 |

### 连接断了先问服务器，再决定要不要重发

页面的重发规则：**只有服务器明确说「没有这一轮」时才重发一次**，其余一律不重发，然后交给 `/partial` 接上。

| 服务器说 | 页面怎么做 |
|---|---|
| `streaming` | 服务器还在写，继续轮询等它写完 |
| `finished` | 答案写完了，用 Redis 里的文字收尾 |
| `failed` | 上游断了，显示「消息生成失败」 |
| 没有这一轮 | 请求没落地，重发一次是安全的 |
| 问不到 | 不知道，不重发，免得生成两遍 |

### Redis 不通时降级

Redis 的写失败只记警告，聊天照常走。页面上会出现一条常驻横幅：「半截回答功能不可用」。

Redis 客户端也改了：连接不通要马上知道（默认的连接重试会让一次失败的写入等 3.7 秒，把整个服务卡住）。

### 状态接口

`GET /api/status` 报两个字段：`{"database": "ok"|"unavailable", "reply_store": "ok"|"unavailable"}`。不需要登录，只带 cookie 也不刷新登录有效期（它是心跳）。页面每 30 秒查一次，标签页重新可见时补查一次。

## 停止：用户按了停止

等回答的时候，发送按钮换成停止按钮。

### 页面这边

- 每次发问都带一个 `AbortController`。按停止时先 `abort()`：正在读的流当场断开，页面不等了。
- 同时调 `POST /api/sessions/{会话id}/abort`，请求体里带上这一轮的编号。
- 停完之后，页面去读 `GET /api/sessions/{会话id}/partial`，问服务器这一轮到底怎么样，按服务器说的显示：
  停了就显示聊天区顶部的警示框「对话已停止」；还在写就接着等；写完了就把答案补上。
  页面不自己宣布停了。
- 这一轮已经写出文字的，那半截留着；一个字都没写出来的，气泡去掉。
- Redis 里的状态多了 `aborted`。页面轮询 `/partial` 时看到它就收尾，不再等。

### 服务器这边

- 中止接口先写一个停止标记（Redis，键是 `h2botapp-chat:{会话id}:stop`，值是这一轮的编号，
  一分钟过期），再取消正在跑的任务。写标记在前，是为了让「停止请求先到」也生效。
- 每场会话正在跑的那一轮记在一张表里（`_running`）。中止接口按会话 id 找到那个任务并 `cancel()`，
  然后等这一轮真的收尾（最多两秒），这样页面随后读到的就是最终状态，不是还在写的中间状态。
- 任务被取消时 `_relay` 记下 `aborted` 再把取消往上抛。已经写出来的半截文字留在 Redis 里。
- 上游的连接随任务一起关掉。FastGPT 走的是 v1 接口，它判「这一轮停了」的标准就是客户端断开
  （v4.14.5 源码 `packages/service/core/workflow/dispatch/index.ts`），所以断掉连接就等于告诉它别写了；
  它会在下一个节点边界停下，已经在跑的那个节点会跑完。
- 对话接口在开这一轮之前先看停止标记：编号对得上，说明用户已经按过停止，
  这一轮不开，只把提问登记下来（刷新以后还能看到「问了什么、这一轮被停了」）。

### 为什么要有停止标记

只有「取消正在跑的任务」是不够的。停止请求和对话请求是两条 HTTP 请求，服务器按到达顺序处理：
如果停止请求先到，那一轮还没登记，没有任务可取消，停止就白按了 —— 那一轮照跑完，页面却说停了。

实测过这种次序：对话请求走一条新连接、停止请求走一条已经连着的空闲连接时，
停止的字节先到服务器，十次里有十次停不掉。

有了停止标记就不管谁先到：停止请求把编号记下来，后到的对话请求看到编号对得上，自己就不开这一轮。
标记按编号认，只对那一轮有效，下一轮照常。

实测（2026-10-31）：停止先到 → 上游一次都没被问，流直接结束，
`/partial` 是 `{"status":"aborted"}`；对话先到 → 那一轮被掐掉，`/partial` 同样是 `aborted`；
老客户端不带编号 → 服务器自己认当前这一轮，照样掐掉；停过之后发新一轮 → 正常跑完。

### 页面断开不算停止

刷新页面、关掉标签页，浏览器也会断开这条流。这时服务器**不**取消那一轮，它照旧写完，
页面回来还能接上（这是「刷新后接上」的前提）。所以「停止」必须由页面明确说一声，
不能拿连接断开来判断。

### 为什么不用 FastGPT 自己的停止接口

v4.14.5 有 `POST {访问地址}/v2/chat/stop`（body 是 `{appId, chatId}`），认 API key，我们部署上也有，
调它会返回 `{"success": true}`。但它写的 Redis 标记只有 v2 调用会读，我们走的是 v1：实测在回答进行到
第 1 秒时调它，连做 4 次，每一轮都照跑完、都有完整回答、都有 `[DONE]`。

所以停一轮靠的是我们自己断开到上游的连接（cancel 掉 httpx 请求）。详见 [FINDINGS.md](FINDINGS.md)。

### 一个已知的副作用

FastGPT 那边会把这一轮的「用户提问」记进它自己的历史，即使这一轮被掐掉了。
刷新之后线程里可能看得到一条没有回答的提问。我们的库里没有消息表，那条提问只存在 FastGPT 那边。

实测（2026-10-30）：发一条提问，1.5 秒后调中止接口，`/partial` 返回
`{"status":"aborted","text":""}`，日志里中止之后再没有「发给页面」的记录，
FastGPT 的历史里多了一条只有提问的记录。

## 每一轮有编号了：刷新以后接得上

### 编号从哪来

页面每次发问生成一个编号（UUID），两处都用它：发请求时带上，Redis 里也存着。
FastGPT 那边也有位置放它 —— 请求体里的 `responseChatItemId`，传了它，FastGPT 就把这个值
当作本次回答的 ID 存进数据库（实测：那条 AI 记录的 `dataId` 就是我们的编号）。

所以一个编号同时出现在三个地方：页面的消息上、Redis 里、FastGPT 的历史里。
不管刷新多少次，都能认出「哪一条是当前这一轮」，不用再靠文字去猜。

### Redis 里现在存什么

| 键 | 内容 |
|---|---|
| `h2botapp-chat:{会话id}:status` | `streaming` / `finished` / `failed` / `aborted` |
| `h2botapp-chat:{会话id}:text` | 已经写出来的半截文字 |
| `h2botapp-chat:{会话id}:turn` | 这一轮的编号和用户问的话 |

### 线程接口把两半拼起来

`GET /api/sessions/{会话id}/messages` 现在返回整场会话的线程：

- FastGPT 的历史（写完的轮次都在里面）；
- 再加上 Redis 里当前这一轮：用户提问 + 一个「正在写」的回答。

拼的时候看编号：历史里已经有这个编号的回答（说明这一轮写完了，FastGPT 已经记下了），就不再补；
没有才补。提问如果历史里已经有了（失败或被停止时 FastGPT 也会记下提问），也不重复添。

实测（2026-10-30）：发出提问后刷新，`GET /messages` 返回两条 —— 用户提问，和一个
`waiting: true` 的回答。提问和三个点都在了。

### 同一场会话同时只跑一轮

`POST /api/chat` 现在检查这场会话是不是已经有一轮在写。是的话回 409，不开新一轮。

以前可以同时开两轮：FastGPT 那边多出一轮对话，Redis 里的半截文字被 `begin_reply` 清掉重来，
两轮的片段交错着写在一起。页面上孩子把同一条问题再发一遍就能触发。

页面收到 409 的处理：把问题放回输入框，提示「这场对话还有一条正在回答，等它答完再发」，
然后重新读一次线程，把正在写的那一轮显示出来。

### 刷新得太急不会把上游打垮

服务器留五秒的历史缓存：刷新多少次，上游就只被问一次。

以前每刷新一次就问一次上游要整段历史，21:18 那次连着刷新十来次，上游连不上了
（`httpx2.ConnectTimeout`），聊天本身也失败。详见 [FINDINGS.md](FINDINGS.md)。

## 重试按钮

上游中途失败时，除了「消息生成失败」，还给一个「重试」按钮。这件事做掉了（2026-10-31）。

### 上下文拼接归谁

**归 FastGPT，不归我们。**

我们发给 FastGPT 的请求体里只有当前这一句：

```json
{
  "appId": "...",
  "chatId": "...",
  "stream": true,
  "detail": false,
  "messages": [{"role": "user", "content": "用户这次问的"}]}
]
```

FastGPT 的接口文档写着：chatId 非空时，它自己去数据库取这场会话的历史，把 messages 数组最后一条当用户问题，其余忽略。所以上下文不用我们拼，页面也不用管。（文档站对应的是更新版本，这两条在 v4.14.5 的源码里同样成立，详见下面一节和 [FINDINGS.md](FINDINGS.md)。）

「重试」按钮要重发的是哪一句，也在页面这边：就是那条半截回答前面的用户提问，页面的消息列表里本来就有。

### 上下文拼接归谁：两个写法，用哪个要想清楚

官方文档的原文（[对话接口](https://doc.fastgpt.io/zh-CN/openapi/chat)）：

- chatId 传非空字符串：FastGPT 自动从它的数据库取这场会话的历史，把 messages 数组**最后一个**内容当用户问题，其余 message 全部忽略。
- chatId 不传：不用 FastGPT 的上下文功能，**完全靠传入的 messages 构造上下文**。

这两条在 v4.14.5 的源码里同样成立（我们早前也实测过）。FastGPT 一次带几轮历史，是它应用里的
「记忆轮数」定的：v4.14.5 的 AI 对话节点默认 6（`dispatch/ai/chat.ts` 里的 `history = 6`），
`getHistories` 取最后 6×2 条记录，并保留开头的 System 消息。这个值在我们这边改不了。

也就是说，想要自己掌握上下文（自己存、自己拼、想改想重发），就不能传 chatId，得把整段对话作为 messages 发过去。
代价是 FastGPT 那边不再有这场会话的记录，我们的 `GET /api/sessions/{会话id}/messages` 也就没有东西可读，
历史只能读我们自己的库。好处是「删掉上一轮再重发」这类操作变得平常：历史是我们自己的，删一条就行。

### 删一条消息：官方文档里没有，源码里有

[官方接口文档](https://doc.fastgpt.io/zh-CN/openapi/chat)能查到的删除只有「删除对话」：
`DELETE {访问地址}/core/chat/history/delHistory?chatId={会话id}&appId={应用id}`。
FastGPT 源码里这个接口的注释是 "delete single chat history (soft delete)"，
它把整场会话标记成删除，也就是**清空整场上下文**，不是删掉其中一轮。

删单条记录在 v4.14.5 里是：

```
POST {访问地址}/core/chat/item/delete
body: {appId, chatId, contentId}
```

它给那条记录写 `deleteTime`（软删），按 `dataId` 匹配。官方文档没有列它，地址、参数和鉴权方式
要自己对着源码看（FastGPT 仓库 tag v4.14.5 的 `projects/app/src/pages/api/core/chat/item/delete.ts`）。
鉴权走 `authChatCrud`，API key 可以 —— 我们的部署上实测过（2026-10-31）。

对我们的用处：我们的 `responseChatItemId` 就是那条 AI 记录的 `dataId`，所以 `contentId` 传我们的
turn id 就能精确删掉那一轮。

（早先这里写的 `core/chat/record/delete` 和 `sourceType`/`sourceId`/`contentIds` 那套参数属于更新版本，
v4.14.5 没有那个文件。）

### 每一轮的编号：FastGPT 有一个位置放我们的编号

官方文档里有 `responseChatItemId`：传了它，FastGPT 就把这个值当作本次回答的 ID 存进数据库，
并要求同一个 chatId 下唯一。也就是说「这一轮的编号」不用自己想办法编号，把自己的编号传过去就行。

这一条已经在用了：每次发问我们生成一个 UUID 放在请求体的 `responseChatItemId` 里，
实测那条 AI 记录的 `dataId` 就是我们的编号（见上面「编号从哪来」那一节和 [FINDINGS.md](FINDINGS.md)）。

### 截掉上一轮再重发

重发用同一个 chatId、再发同一条用户消息就行。但这样 FastGPT 的历史里会**多出一轮**（又一条用户消息 + 一条新的助手消息），页面读历史时会看到两遍。

要干净，得把上一轮留在上游的记录删掉。地址和参数见上面「删一条消息」那一节（v4.14.5 的
`core/chat/item/delete`）。

### 页面上是什么样

- 失败的回答下面那条红框里写着「消息生成失败」，红框下面一个「重试」按钮（三种语言都有）。
- 点下去以后：失败的回答和那条提示去掉，用户提问留在原处，新的答案接着写在那里。
- 刷新页面以后失败还在：服务器在历史里把失败的那一轮标成 `failed`，页面照旧显示提示和按钮。

失败提示按位置找它的提问：刷新以后看到的提问是上游的记录，上游不知道我们的编号，
所以按「失败提示前面最近的一条提问」来认。

### 重发怎么做

`POST /api/chat` 多一个可选的 `retryOf`（要重发的那一轮的编号）。服务器收到以后：

1. 先把上一轮在上游留下的记录删掉；
2. 再照常开新一轮（新的轮次编号，`responseChatItemId` 也是新的）。

### 上游那一轮留下了什么

两种情况，删法不一样：

- **工作流跑完了**：上游的记录里有这一轮的回答，`dataId` 就是我们的编号。按编号找到它，
  删掉它，再删掉它前面那条提问（提问的编号是 FastGPT 自己的）。
- **工作流没跑完**：上游只留下提问那条记录。这时只有当它就是最后一条记录时才删 ——
  这一轮是最近的一轮；失败以后用户又问了别的，那条记录就不是我们的，不能删。

找不到就不删：宁可让历史里多一遍问答，也不要删掉别人那一轮。

找记录要删的时候不能读缓存：缓存里可能是这一轮之前的那份，少了刚写上去的那条。

### 同一个请求来两次

服务器拿请求里的编号对一下 Redis 里记着的当前轮次：对得上就是同一个请求又来了（重复点击、
页面重发），不再开一轮。已经在写的那一轮回 409，已经写完的那一轮回一个空的流 ——
页面读 `/partial` 就能知道这一轮到底怎么样。这样同一个请求发两次只生成一遍。

### Redis 里那半截文字在重发时怎么清

`begin_reply` 会把文本 key 删掉重来（实测就是这样），不用另外写代码。

### 还留着的

- 上下文归谁：还是没定。现在传 chatId，历史在 FastGPT 那边。
- 我们自己的库里还是只有会话，没有消息表。历史全靠 FastGPT 那边；FastGPT 那边挂掉或清掉记录，
  页面就没有历史了。
- 被用户按了停止的那一轮，FastGPT 那边还是会记下那一句提问（已知的副作用）。
  重试按钮只给失败的回答，停止的不给。
