# 回答中断：现在的做法和接下来要做的

## 现在是什么样

一轮回答从后端到页面是这样走的：

- 页面 `POST /api/chat`，后端起一个后台任务去问 FastGPT，页面从一条 SSE 连接里读。
- 流里只有两种东西，都是 FastGPT 的原样：`data: {"choices":[...]}` 是正文，`data: [DONE]` 是「写完了」。
- 后端把这一轮已经写出来的文字记在 Redis 里（`h2botapp-chat:{会话id}:text`），同时记一个状态：`streaming`（还在写）、`finished`（写完了）、`failed`（中途断了）。
- 页面断流之后读 `GET /api/sessions/{会话id}/partial`，就知道服务器那边到底怎么了。

上游中途失败时，实际发生的是：

1. 后端转发了几块内容，然后发现连接断了，把状态记成 `failed`，已写出的文字留着。
2. 流直接结束，没有 `[DONE]`。
3. 页面看到「流结束但没有 `[DONE]`」，判定「没写完」，去读 `/partial`。
4. 状态是 `failed`，于是显示「响应中断」的错误提示，位置在助手那条（半截）回答的下面。

这段是实测过的：用一个只会发一块内容就断线的假上游跑过，聊天接口吐出一块内容后没有 `[DONE]`，`/partial` 读出来是 `{"status":"failed","text":"..."}`。

上游在一开始就失败（连不上、密钥不对、地址没配）时不一样：那还是 HTTP 错误，页面显示「服务器错误」。

## 这次定下来的几件事

### 对页面的约定只有三条

| 页面看到 | 意思 |
|---|---|
| 200 + `[DONE]` | 写完了 |
| 200 + 流结束但没有 `[DONE]` | 没写完 |
| 非 200 + `{"detail": ...}` | 后端没接下 |

流里不增加任何新格式，只用 FastGPT 现有的两种帧。页面的解析代码可以照着 FastGPT 的接口文档写。

### 三个超时

现在 `read=None`（无限等），上游接了连接一直不吭声，这一轮会永远挂着，页面的三个点也永远转。要补三个上限：

| 位置 | 建议值 | 依据 |
|---|---|---|
| 连接 | 10 秒（现状） | httpx 的 connect 超时 |
| 发出请求 → 收到上游第一个字节 | 30 秒 | 实测 0.3 到 5.2 秒 |
| 两个字节之间 | 60 秒 | 上游是一整块给，间隔接近 0 |

### 探活

后端每隔 30 秒探一次上游，结果记在内存里，三处用：

- `POST /api/chat` 进来时已知上游不通 → 直接回 503，不用开流。
- `GET /api/status` 给页面做「后端不健康」的常驻横幅。
- 回答「这一轮到底写完了没」。

### Redis 不可用时降级

Redis 写失败只记警告，不拦聊天。页面要知道「半截回答功能不可用」。

现在页面上的提示是会自己消失的 toast，常驻提示要另做：聊天区顶部一条不消失的横幅，两种文案分开——「无法连接到服务器」（请求发不出去）和「半截回答功能不可用」（聊天还能用，但刷新接不上、断了接不回来）。

### 重发的那一套

请求发了出去、响应还没回来时断网，页面会自动重发，服务器就会生成两遍。堵法：

1. 后端在回响应之前就登记「这一轮开始了」（把 `begin_reply` 从后台任务挪进请求处理）。
2. 页面断流之后读 `/partial`：状态是 `streaming` → 服务器还在写 → 继续轮询，不重发；状态是空的 → 请求确实没落地 → 重发一次是安全的。

## 接下来要做的：重试按钮

上游中途失败时，除了「响应中断」，还给一个「重试」按钮。

### 上下文拼接归谁

**归 FastGPT，不归我们。**

我们发给 FastGPT 的请求体里只有当前这一句：

```json
{
  "appId": "...",
  "chatId": "...",
  "stream": true,
  "detail": false,
  "messages": [{"role": "user", "content": "用户这次问的"}]
}
```

FastGPT 的接口文档写着：chatId 非空时，它自己去数据库取这场会话的历史，把 messages 数组最后一条当用户问题，其余忽略。所以上下文不用我们拼，页面也不用管。

「重试」按钮要重发的是哪一句，也在页面这边：就是那条半截回答前面的用户提问，页面的消息列表里本来就有。

### 截掉上一轮再重发

重发用同一个 chatId、再发同一条用户消息就行。但这样 FastGPT 的历史里会**多出一轮**（又一条用户消息 + 一条新的助手消息），页面读历史时会看到两遍。

要干净，得把上一轮那条助手消息删掉。FastGPT 的接口清单里有「删一条消息」这个操作，但 `docs/FINDINGS.md` 只记了有这么个操作，没记地址和参数，要用得先查。

还有一个竞态：如果是我们这边超时放弃的，FastGPT 那边可能还在生成，那条记录过一会儿才落库，删除得等它出现。

### 待定

- 「重试」点下去之后，后端要不要带一个请求 id，让服务器认出「这是同一个请求的第二次」，而不是新的一轮。
- 删除上一轮助手消息的具体接口：地址、参数、能不能删指定的一条。
- Redis 里那半截文字在重发时怎么清。现在 `begin_reply` 会把文本 key 删掉重来，看着是自动的，但要实测。
